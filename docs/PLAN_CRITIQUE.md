# Assessment of the Original Plan

**Status:** Superseded-plan assessment. The corrections below are binding through `PLAN_V2.md`. The evidence base is the root legacy directives, the inventory/migration documents, and the inspected Kotlin core.

| Finding | What the original plan said | Why it is wrong or risky | Correction in `PLAN_V2.md` |
|---|---|---|---|
| 1. Contradictory Firebase architecture | `CANONICAL_MODULE_MAP.md` assigns Cloud Functions paths, Firestore roots, Pub/Sub topics, and schedulers; `FIREBASE_NATIVE_SCAFFOLD.md` calls Firestore system state; `bootstrap-firebase.sh` initializes Functions, Firestore, and Hosting. | This directly conflicts with the stated Firebase/Firestore-free, local-first direction and creates two incompatible authorities. | v2 formally supersedes these directives and uses a local SQLite event log with optional cloud adapters only. The deletion manifest identifies the conflicting files for retirement. |
| 2. CI/CD placed at Phase 19 | The original master plan treated CI/CD as a late activity while prior phases allowed validation only as tooling permitted. | A hard gate that arrives after most implementation cannot prevent regressions in the work that precedes it. | Phase 0.5 establishes `gradle verifyAll` in CI, test artifacts, and merge controls before feature expansion. |
| 3. Security too late | Security was deferred until after work that could introduce credentials or execution paths. | Credential isolation and approval boundaries must precede any capability that can request signatures, transmit secrets, or move value. | v2 splits security into Phase 8a credential/custody controls and Phase 8b policy/simulation mediation. |
| 4. Prediction before outcome history | Prediction was scheduled before memory and learning, although calibration needs observed outcomes. | Confidence claims cannot be evaluated without a versioned prediction, a feature fingerprint, and a later outcome record. | Phase 3 contains prediction outcome event types and Phase 10 adds prediction only after the outcome journal and source provenance exist. |
| 5. Unachievable determinism | Phase 5 required determinism without first controlling ambient time. | A direct wall-clock read changes otherwise identical executions and invalidates replay. | Phase 1 uses the `Clock` port and `MutableClock`; Phase 5 adds replay and static determinism checks. |
| 6. Unfalsifiable gates | Several phase gates were statements of intent rather than commands or assertions. | Reviewers cannot consistently decide whether a phase is complete, and regressions can pass unnoticed. | Every v2 phase names a failing command, test, benchmark comparison, or static rule. |
| 7. Missing workstreams | M09 social, M11 governance, and M13 identity were absent from the phase list. Schema migration, testing strategy, and observability were also not delivered as workstreams. | Omitting domains from the sequencing creates unowned code; omitting evolution, testing, and diagnostics makes local persistence unsafe to extend. | Phases 4–6 establish evolution, replay/testing, and observability. Phases 7 and 12 explicitly schedule social, governance, identity, and sports analysis. |
| 8. Opaque module directories | The plan used bare M00–M20 directory identities. | Numeric paths conceal responsibility and do not scale for navigation or dependency review. | v2 uses domain-named modules and retains M00–M20 only as `ModuleId` metadata. |
| 9. Phone-based autonomous custody | The original direction included automated on-chain execution. | A phone can be lost, compromised, or killed by the OS. An autonomous hot key with spend authority increases loss exposure and weakens meaningful user consent. | v1 is observation and simulation only. Any later signing requires hardware-backed, explicit approval and a policy-mediated path. |
| 10. Sports-betting jurisdiction | The original plan did not address jurisdiction for sports-betting functionality. | Sports wagering and data use are regulated and location-dependent; the owner is in Indiana. | v2 confines the module to Signal-based analysis and EV computation, adds an Indiana jurisdiction notice, and forbids wagering/account adapters in v1. |
| 11. Floating-point finance | Legacy Python and TypeScript financial paths use float, `Double`, or `number` values. | Binary floating point can lose decimal precision and makes balance, reserve, and EV invariants unreliable. | `Amount` wraps `BigDecimal`; v2 makes decimal-only financial paths a Definition-of-Done requirement. |
| 12. Missing operational decisions | The original plan omitted SLOs, Definition of Done, cloud cost, rollback, accessibility, licensing/IP, and the KMP-versus-Android decision. | Without these, implementation can appear complete while being unusable, unauditable, costly, inaccessible, or difficult to reverse. | v2 adds phone budgets, completion criteria, cost formula, recovery rules, accessibility gates, licensing/IP review, and ADR-0013. |

## Evidence from the current rebuild

The correction is not only aspirational. `core:contracts` implements `Clock`, `Outcome`, `PlatformError`, and domain-named `ModuleId`; `core:domain` implements `Amount`, predictions, signals, and treasury invariants; `core:eventbus` implements schema-versioned envelopes and an append-only `EventStore`; `core:persistence` implements forward-only SQLite migrations; and `core:policy` implements ordered fail-closed decisions. Existing reports show 183 passing JVM tests with zero failures across domain, persistence, policy, eventbus, and runtime. This is baseline evidence, not a claim that the product is production-ready.
